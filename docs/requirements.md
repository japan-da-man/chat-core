# Requirements

## Purpose

この文書は、`chat-core` の MVP と将来拡張を切り分け、先に確定すべき要求を整理するための要求一覧です。

## Product Direction

`chat-core` は Slack 寄りのチャット体験を参考にしますが、最初から Slack を完全に再現することは目指しません。まずは会話、参加者、メッセージ、スレッド、既読、新着通知、検索の最小集合を成立させます。

## MVP Functional Requirements

Phase 1 で対象にする要求:

- 外部認証済みユーザーを内部 API 経由で登録できる
- DM とグループ会話を作成できる
- 会話作成時に WebSocket で新規会話通知を送れる
- グループ会話作成時にタイトルと初期参加者をまとめて指定できる
- グループ会話の `owner` が参加者を追加できる
- グループ会話の `owner` がタイトルを編集できる
- テキストメッセージを送信できる
- スレッド返信を送信できる
- メッセージ送信時に `mentioned_user_ids` を受け取ってメンションを記録できる
- 自分が送信したメッセージを編集できる
- 自分が送信したメッセージを削除できる
- 会話内メッセージを順序付きで取得できる
- スレッド内返信を順序付きで取得できる
- 会話一覧を取得できる
- 通常会話の既読位置を更新できる
- スレッド既読位置を更新できる
- 未読件数を取得できる
- 会話一覧で `has_unread_threads` を参照できる
- 新着メッセージを WebSocket で通知できる
- 自分が参加している会話を横断検索できる
- 特定会話内を検索できる

## MVP Acceptance Criteria

最初の実装で最低限満たしたい条件:

- 同一会話内のメッセージは `sequence_no` に従って返る
- 同一スレッド内の返信は `reply_seq` に従って返る
- 同じ `client_message_id` による再送では重複メッセージが作られない
- `last_read_message_seq` の更新は後戻りしない
- 配信が失敗しても再取得で整合が取れる
- 会話作成通知を受けたクライアントは DB 正本から会話情報を再取得して整合を取れる
- 会話一覧で各会話の最新メッセージ位置を参照できる
- スレッド返信は通常会話の `unread_count` と会話一覧ソートに影響しない
- 削除された親メッセージは tombstone として残り、配下のスレッド返信は維持される
- メッセージ編集と削除は送信者本人のみ成功する
- 検索結果はヒットしたメッセージ単位で返り、削除済みメッセージは検索対象から除外される

## MVP Non-functional Baseline

Phase 1 で固定する非機能前提:

- 最大同時 WebSocket 接続数は `1,000`
- 1 会話あたりの最大参加人数は `100`
- 1 メッセージ最大文字数は `4,000`
- 新着通知の許容遅延は通常時 `3 秒以内`
- 既読反映の許容遅延は通常時 `5 秒以内`
- 通常会話の順序保証は「会話内の commit 順」
- スレッドの順序保証は「スレッド内の commit 順」
- 検索は日本語メインを前提にし、MVP は `PGroonga` を採用する

## MVP Decisions Fixed

Phase 1 で固定したプロダクト前提:

- Slack 寄りの UX を前提にする
- `tenant` / `workspace` は持たず、全ユーザー同一空間にする
- 認証は外部の Application API が持ち、`chat-core` は内部 API として使う
- `chat-core` は受け取った `user_id` を前提に会話参加者ベースで認可する
- 1 対 1 DM は同じ 2 人につき 1 会話だけ作る
- グループ会話は `title` 必須、`owner` と `member` を持つ
- 参加前ログは閲覧可能にする
- 再参加後も過去履歴は閲覧可能にし、未読は再参加時点でリセットする
- スレッドは Slack 型の 1 階層だけにし、DM にも許可する
- スレッド返信は通常会話の新着、未読、会話一覧ソートに数えない
- スレッド未読は `親投稿者 / スレッド投稿者 / スレッド内メンション対象者` だけを対象にする
- メンション対象の解決は Application API 側で行い、`chat-core` は membership を検証する
- 検索は MVP に含め、全会話横断検索と会話内検索の両方を提供する
- 検索ソートは `relevance` と `newest` を持ち、デフォルトは `relevance`
- 監査ログは持つが、編集前本文の履歴テーブルは持たない

## Deferred Decisions

MVP では固定せず、後続で決める論点:

- 添付ファイル保存基盤と最大サイズ

- 管理者削除やモデレーション権限
- 監査ログの外部エクスポート
- 将来のマルチテナント対応

## Implementation Flow

実装は次の順で進める想定です。

1. 未確定論点を絞り込み、MVP の前提を固定する
2. `Cargo.toml`、`src/`、`migrations/`、`tests/` などの土台を作る
3. `users`、`conversations`、`conversation_members`、`messages`、`message_mentions`、`thread_members`、`search_documents`、`audit_logs`、`outbox_events` の初期スキーマを作る
4. 会話作成、メッセージ送信、スレッド返信、編集、削除、既読更新の command 側を実装する
5. 会話一覧、会話詳細、メッセージ一覧、スレッド一覧、検索、未読件数の query 側を実装する
6. `conversation.created` と message event の WebSocket 通知、検索更新 worker、監査ログ記録を実装する
7. integration test で順序保証、冪等送信、スレッド未読、検索反映、再取得による整合回復を確認する
